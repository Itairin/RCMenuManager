# 新功能：拖入即识别（本轮）

- **时间**：2026-11-17
- **测试**：218 → **225**；Debug / Release 均 0 警告 0 错误

## 行为

1. 把文件 / 文件夹 / 驱动器拖到窗口上 → 顶部出现拖拽提示层（原有），松开后：
   - 自动切到对应「类」作用域（文件夹 / 驱动器 / 该扩展名），
   - **菜单按这个真实对象读取**，而不是临时样本文件，
   - 顶部横幅写明「菜单来自拖入的<类型>：<路径>」，并说明**修改写入的是这一类**。
2. 拖入文件夹后，横幅上可切换 **看文件夹本身** / **看文件夹空白处**（两种菜单不同）。
3. 点「回到通用作用域」清除目标，回到按类浏览。
4. 列表里的修改（编辑 / 启停 / 删除 / 新增子项）照常可用；shell 扩展提供的行仍为只读。

## 关键改动

| 位置 | 改动 |
|---|---|
| `Models/DropTarget.cs`（新增） | 目标模型：路径 + 类型 + 标签 + 「修改影响整类」的说明 |
| `IShellContextMenuReader.TryRead(scope, extended, targetPath)` | 支持按真实路径读菜单；**缓存键包含目标**，否则换一个文件会复用上一个的菜单 |
| `ShellContextMenuReader.Read` | 目标为文件夹且作用域是「文件夹背景」时走背景读取接口 |
| `MainViewModel.DropTarget` | 目标变化即重载；预览页与预热也使用同一目标 |
| `MainWindow.xaml` | 目标横幅 + 只读/未显示提示；文件夹菜单切换按钮 |
| `Converters/EnumEqualsToVisibilityConverter`（新增） | 按目标类型显示对应切换按钮 |

## 过程中发现并修掉的问题

1. **「空白处」和「文件夹本身」读到同一份菜单** —— 读取时优先用了目标路径，却没用背景读取接口，两个按钮看起来没用。
2. **只读行的标题重复**（`打开` / `打开`）—— 我把 `VerbName` 填成了标签本身，行内两列都显示同一个词。
3. **只读行被误标「系统内置」** —— 来源分析不认识 shell 提供的行。新增 `MenuItemSource.ShellProvided` → 徽章显示「扩展提供」。
4. **渲染工具**：`Sleep` 阻塞 UI 线程导致异步加载永不完成（改为泵消息帧）；`MainWindow` 的 pack:// 图标在独立进程解析不到（去掉整窗渲染）。

## 实测（真实文件）

| 拖入对象 | shell 菜单行 | 合并后列表 | 说明 |
|---|---|---|---|
| `note.txt` | 28 | 29 | 含「在记事本中编辑」「转换为PDF格式」等该类型专有项 |
| `archive.zip` | 27 | 27 | 含「全部解压缩(T)...」，与 .txt 的菜单不同 |
| 同一文件夹（空白处） | 22 | 19 | 查看/排序/刷新/粘贴/新建… |
| 同一文件夹（本身） | 31 | 36 | 打开/固定到快速访问/UltraISO/ChatGPT… |

两次不同目标读到的菜单不同 = True（缓存键区分目标）。

## 已知限制

- 一次拖入多个对象时只取第一个（多选对象的合并菜单需要 shell 的 IShellItemArray，当前读的是单选路径）。
- 在这里的修改写入「类」键：对 .txt 的修改影响所有 .txt，不会只影响拖进来的那一个文件。界面横幅已明说。
- 以管理员身份运行后，从非提权的资源管理器拖放会被 Windows 的 UIPI 拦截（系统限制，不是本工具行为）。
